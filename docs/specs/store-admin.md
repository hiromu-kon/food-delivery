# 運営の店舗管理（F-17）

Issue #75 / #76。運営が S-A04 `/admin/stores` で店舗一覧を確認し、S-A05 `/admin/stores/new` と `/admin/stores/:storeId` で登録・編集・スタッフ発行を行う。

## API と認可

`/admin/stores` は [運営認証](admin-auth.md) の認証・現在の運営権限・メール確認・停止判定と Cookie 更新時の Origin 検査を通る。取得・更新ともトランザクションで運営の行をロックし、現在の権限を再確認する。応答は `no-store`。クエリは空のみ、店舗 ID は UUID。入力と応答の項目は `packages/contract/src/store-admin.ts` を正本とする。

- `GET /admin/stores`：店舗名・ID順の一覧。
- `POST /admin/stores`：住所を地図サービスで解決し、座標と一緒に作成（201）。初期状態は受付停止。
- `GET /admin/stores/:storeId`：店舗取得。
- `PATCH /admin/stores/:storeId`：指定項目だけを更新。住所を指定した場合は必ず座標も更新する。住所解決失敗は保存しない。
- `DELETE /admin/stores/:storeId`：削除（204）。メニューとスタッフ所属は cascade で削除し、利用者・資格情報は残す。注文履歴があれば409とし、受付停止を案内する。
- `POST /admin/stores/:storeId/staff`：新規スタッフ発行（201）。既存メールは409。既存利用者の昇格・所属変更・パスワード上書きは行わない。

配達半径は正の有限数（m）、最低注文金額は0〜2147483647の整数（円）。座標・店舗ID・権限の入力は拒否する。座標は API の地図連携で取得し、R-01 の圏内判定は既存 domain を使う。不在店舗は404、不正入力は400、地図の障害は既存の422/503に従う。

## スタッフの発行

パスワードを Better Auth でハッシュ化し、利用者（role=store・メール未確認）、credential、店舗所属を単一トランザクションで保存する。同一メールの競合は DB の一意制約で1件だけ成功する。応答には公開プロフィールのみを含み、パスワード・ハッシュは返さない。

運営は本人へ初期パスワードを安全に伝え、店舗ログイン画面から確認メール送信を案内する。本人が既存の確認メールフローを完了するまでログインできない。削除後にスタッフアカウントが残っていても、所属がないため店舗業務は403となる。

## Web の失敗とライフサイクル

layout と各ページで運営権限を確認し、ブラウザでの通信にも認証 Cookie を付ける。401/403 は運営ログインへ戻す。読み込み失敗は再試行、更新結果不明は再読み込みで保存状態を確認するよう案内する。操作中は二重送信を防ぎ、画面離脱時には要求を中止して古い結果を表示しない。削除は画面内で確認してから送信する。
