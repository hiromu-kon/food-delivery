# 運営認証（F-16）

Issue #71 / #72。ログインは既存の `POST /auth/sign-in/email`、ログアウトは `POST /auth/sign-out` を使う。Cookie・署名付き Bearer・Origin 検査・レート制限・セッション更新は [共通認証](auth.md) に従う。F17–19 の店舗・配達員・注文管理は含めない。

## API の認可境界

`GET /admin/me` は `{ user }`（本人の公開プロフィールのみ）を返す。`adminMeResponseSchema` を contract に置き、RPC の型は `AppType` から導出する。認証・認可後に空の strict query を検証し、余分な ID・role などは 400 にする。

`/admin` 配下は共通の `requireSession` → `requireRole(['admin'], true)` を通る。DB の現在の利用者を読み、未認証・失効・期限切れ・削除済みは 401、運営以外・停止済み・メール未確認は 403。変更は既存セッションの次の要求にも反映する。応答は `no-store`。今後追加する保護 API もこの境界を通し、更新時は更新 SQL / トランザクションでも権限の変更を扱う。

## 初期運営の発行（R-14）

DB マイグレーションを適用した後、API の実行環境に以下を設定し、リポジトリルートで `pnpm --filter @repo/api bootstrap:admin` を実行する。実行者が本人のメールアドレスを確認済みであることを前提に、メール確認済みの運営を作る。

- `DATABASE_URL`: 発行先 DB
- `ADMIN_NAME`: 氏名（1〜100 文字）
- `ADMIN_EMAIL`: 確認済みメールアドレス
- `ADMIN_PASSWORD`: 初期パスワード（8〜128 文字）
- `ADMIN_PHONE_NUMBER`: 電話番号（数字 10〜15 桁、先頭 `+` は任意）

秘密情報は秘密管理基盤や非公開の環境変数から渡し、コマンド履歴・ログ・リポジトリに記録しない。実行後は発行用の環境変数を解除する。パスワードは Better Auth のハッシュで保存する。利用者と credential を単一トランザクションで作り、同時実行は DB の advisory lock で直列化する。既に運営がいる場合や同じメールが使われている場合は失敗し、既存利用者の昇格・パスワードの上書きは行わない。運営が停止中でも再発行しない。一般の運営アカウント管理 API は提供しない。

## Web

`/admin/login` が S-A01。メール・パスワードを入力し、ログイン後に `/admin/me` で運営権限を確認して `/admin` へ進む。権限がなければセッションを失効させ、管理者への問い合わせを案内する。ログアウトに失敗したときは再試行するまでログインフォームを無効にする。

`/admin/(signed-in)` の layout と保護ページの両方でサーバーから Cookie を転送して認可を確認する。未認証は `/admin/login`、403 は `/admin/login?reason=denied` に移す。認証済み画面は運営としてログイン中の案内、本人メール、ログアウトのみ。業務機能のダミーリンクは置かない。

ブラウザでも画面遷移・復帰時に再確認し、確認中・通信失敗時は保護画面を隠す。古い要求の応答は画面離脱・新しい確認・ログアウト後に反映しない。通信失敗は未認証と区別して再試行を案内する。トークンを localStorage に保存しない。
