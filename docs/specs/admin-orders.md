# 仕様：運営の注文管理（F-19）

Issue #83 / #84。F-16 の運営認証を使い、各取得・更新で現在のロール・停止状態・メール確認を検査する。Cookie 更新は許可済み Origin が必要。応答は `Cache-Control: no-store`。

## API

| エンドポイント                    | 用途                                                         |
| --------------------------------- | ------------------------------------------------------------ |
| `GET /admin/orders`               | 注文を作成日時・IDの降順で最大100件取得                      |
| `GET /admin/orders/:id`           | 注文明細、配送先、金額、状態・決済状況、担当配達員ID、履歴   |
| `POST /admin/orders/:id/cancel`   | 受付後・配達完了前のキャンセルと配達料を含む全額返金（R-08） |
| `POST /admin/orders/:id/unassign` | 配達完了・キャンセル以外の担当解除（R-11）。状態は維持する   |

一覧の任意条件は `status`、`storeId`（UUID）、`date`（YYYY-MM-DD、日本時間の1日）、`id`（注文UUID）。不正な条件・IDは400、不存在は404、許可されない状態は409。共有契約は `packages/contract/src/admin-orders.ts`。決済識別子・注文者ID・座標・内部試行情報は返さない。

## テスト用返金の注入

今回の返金は `createApp({ testRefunds })` の `TestRefundClient` 注入だけを使う。通常の起動では注入せず503となり、注文も変更しない。ネットワークを使う返金実装・ライブAPI・実課金は追加しない。既存チェックアウト用の Stripe クライアントや秘密鍵を返金に転用しない。

注入実装は `mode: 'test'` を持つ。決済取得・返金検索・返金作成の各応答は境界で検証する。決済がテストモード、対象ID、JPY、全額売上確定に一致するときだけ返金する。返金も対象・全額・JPY・テストモードと `succeeded` を確認してから完了とする。

注文行をロックし、キャンセル理由 `admin` と返金開始日時・操作履歴を先に保存する。キャンセル後は店舗などが進行させられない。同じ行を再びロックし、保存された金額と固定キー `admin-refund:<orderId>` で返金を照合する。注入実装の `findRefund` はそのキーの試行を検索し、`refund` は同じキーで重複作成しない契約とする。

応答喪失・DB保存失敗・保留・失敗・不一致は `503 PAYMENT_RECONCILIATION_REQUIRED`。注文はキャンセル済み・決済確認中のまま維持する。同じAPIの再送で既存返金を検索し、確認済みなら返金を重ねない。開始から23時間以降は新規作成を送らず取得だけ行う。返金完了時に返金ID・確認日時を保存し、担当を解除する。自動再試行・本番返金は対象外。

## 履歴とWeb

`/admin/orders`（S-A02）と `/admin/orders/:id`（S-A03）を提供する。検索・再読込、確認ダイアログを挟む全額返金・担当解除、結果不明からの再確認ができる。表示中は5秒ごとに再取得し、離脱・対象変更・認証ガードによるアンマウントで購読・通信を中断し古い応答を反映しない。取得失敗中は変更操作を止める。

状態履歴は本機能導入後の注文作成、注文者取消、店舗の受付・拒否・準備完了、運営取消を同じトランザクションで保存する。導入前の履歴は復元しない。担当解除・運営取消は操作した運営ID・直前状態・担当IDを別途監査記録に残す。既存の配達機能がないベースブランチのため、担当配達員は注文の任意ユーザー参照として保持し、画面には担当IDを表示する。
