# 注文者アプリのお届け先管理（S-C10 / Issue #12）

## 対象

`apps/customer-app` の認証済みルート `/addresses`。アカウント画面から開き、APIに保存したお届け先の一覧・登録・編集・削除を行う。店舗、カート、注文の処理は対象外。

## 表示と入力

- 初回は一覧を取得し、空なら未登録の案内を表示する。再読み込みで最新の一覧を取得できる。
- 住所は必須・200文字以内、建物名／部屋番号と配達メモは任意・各100文字以内。共有 `addressInputSchema` で前後空白を除去して検査する。
- 編集は一覧の現在値を初期表示する。正規化した値を元の値と比較し、変わった項目だけを共有 `addressUpdateSchema` に通してPATCHする。空文字で任意項目を消せる。無変更の保存は通信せず一覧へ戻る。
- 所有者・座標の入力欄は設けず、送信もしない。サーバーが決定した住所データだけを表示する。
- 削除は共通 `AlertDialog` で住所・建物・メモと取り消せない旨を確認する。キャンセルは通信せず一覧を保持する。
- 共通のButton／TextField／Text／NoticeBannerとデザイントークンを使う。既存のStack、下部SafeArea、キーボード回避とScrollViewを維持し、登録・編集の切り替えでナビゲーターを作り直さない。

## 認証と競合

`hc<AppType>` のAPIクライアントを使う。Cookieに依存せず、SessionControllerのprivate tokenを `authenticatedRequest` のコールバック経由でAPI層へ渡す。プロフィールstate、画面props、住所stateにtokenを含めず、画面からSecureStoreを読まない。

401および403（停止・他roleを含む）はセッションを失効させ、保存tokenとプロフィールを破棄する。削除失敗時は既存のセッションエラー画面で再試行できる。セッション世代とtokenを応答後にも検査し、ログアウトや別ログインより古い要求の成功・失効応答を消費させない。通常の同一セッション再確認は住所処理と並行できるが、認証失効時は進行中の要求を無効にする。

住所Controllerは一覧・保存・削除を同期的に排他制御し、連打と処理中のフォーム変更・キャンセルを拒否する。画面破棄・セッション終了では住所stateを破棄し、操作世代で古い応答を無効にする。

## エラーと再試行

400は入力確認、404は一覧再読み込み、422は住所の再確認、503は時間をおいた再試行を案内する。通信エラーも再試行を案内する。保存成功までは入力と既存一覧を変更せず、削除成功までは対象と一覧を保持する。削除失敗の案内は確認ダイアログ内にも表示し、そのまま再試行できる。再読み込み失敗時も直前の一覧を残す。

通信には既存APIクライアントの10秒期限を適用する。通信断でサーバーの処理結果が不明な場合、登録再試行によって重複登録される可能性はある。UIの連打抑止は冪等キーによるサーバー側の重複排除ではない。

## 検証条件

- 単体テストはHTTP fetch mockおよびControllerの遅延Promiseを使用する。差分PATCH、入力制限、キャンセル、二重操作、失敗時の保持、古い応答の破棄、401／403の失効、新しいセッションを古い401で失効させないことを検査する。
- 全体checkのDBは専用 `TEST_DATABASE_URL=postgres://postgres:postgres@localhost:15434/food_delivery_test` を使う。
- iOS SimulatorのUI検証は専用端末、Metro8112、一時HTTP mock18792、`EXPO_PUBLIC_WEB_URL=http://127.0.0.1:3112` の組み合わせを使用する。このHTTP mockは認証とCRUDもメモリ上で代替し、検証用tokenと固定座標を返す。実際の署名検証・DB永続化・地図精度を確認するものではない。製品コードへのmockや固定座標の追加は行わない。
- mockでは住所に `422`／`503` を含めると各エラーを返し、検証用制御で401も返せる。実キーでの測位、課金API呼出しは行わない。
- iOS／Android exportを検査する。実機・Android端末操作とPenpot照合は未確認。スクリーンショットや検証ハーネスはrepo外へ保存する。
