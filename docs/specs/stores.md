# 仕様：店舗検索（F03）

認証済みの有効な注文者が、本人のお届け先を基準に配達エリア内の店舗を取得する。メール確認前でも検索できる。既存のお届け先CRUDは変更しない。

## API

`GET /stores?addressId=<UUID>`

- `addressId` は必須。未知キー・重複キー・クライアントからの緯度経度や所有者指定は400 `VALIDATION_ERROR`。
- 未認証は401、停止アカウント・注文者以外のroleは403。
- DBで認証ユーザーIDと住所IDの両方を照合する。他人の住所と不存在は同じ404 `NOT_FOUND`（「お届け先が見つかりません」）。クライアントの座標を使わない。
- 本人住所の保存済み座標から検索する。住所が未登録なら先に住所CRUDで登録する。検索では地図APIを呼ばない。
- 成功は200 `{ stores: [...] }`。圏内に店舗がなければ空配列。`Cache-Control: no-store`。

## 保存・公開項目

`stores` は店名 `name`、紹介 `description`、店舗住所 `address`、緯度 `latitude`・経度 `longitude`、配達半径 `deliveryRadiusMeters`、最低注文金額 `minimumOrderAmount`（税込整数円）、受付状態 `isAcceptingOrders`、写真URL `photoUrl`（nullable）を保存する。IDはUUID。半径は正の有限メートル値で初期値3000、最低注文金額の初期値は0、受付状態の初期値はtrue。緯度は[-90,90]、経度は[-180,180]。DB制約で値域を保護する。

一覧は上記の店舗項目と `id`、計算済み `distanceMeters`、`canOrder` を返す。保存モデルの型はDBからcontractへ導出する。注文者の住所・座標・建物・配達メモ・ユーザーID、認証情報は返さない。

`canOrder` は検索時点の受付状態による注文可否を示し、`isAcceptingOrders` と一致する。R-09により停止店舗もエリア内なら一覧に残し、両方falseを返す。これは注文確定の保証ではなく、最低注文金額・メール確認などの注文条件の判定と、確定時の受付状態の再確認は後続F06の責務。

受付状態の変更は [受付の切替（F-12）](store-acceptance.md) を参照する。変更後の検索も毎回保存済みの受付状態を返す。

## 距離と順序（R-01）

WGS84の経緯度を度で受け取り、半径6,371,008mの球面上の大円距離をHaversine式で求める。道路距離・標高・楕円体による補正は扱わない。球面モデルと単位は[PostGIS ST_DistanceSphere](https://postgis.net/docs/ST_DistanceSphere.html)の既定半径・メートル単位を参照。式は `a = sin²(Δ緯度/2) + cos(緯度1)cos(緯度2)sin²(Δ経度/2)`、距離は `2R asin(√a)`（角度をラジアンへ変換し、浮動小数点誤差対策でaを[0,1]に制限）。

距離計算・半径判定はdomainの純関数に置く。不正な座標・NaN・無限大・負の距離・非正の半径を拒否する。`distanceMeters <= deliveryRadiusMeters` で境界を含める。比較前も応答時も丸めず、表示の丸めによって境界を変えない。

距離の昇順、同距離はUUID文字列の昇順で返す。N04の最大100店舗を想定し、本人住所1件と全店舗をそれぞれ一括で読む。店舗ごとのSQLや外部呼出しはない。将来規模を広げる場合は空間検索・ページングを別途検討する。

## 範囲外

店舗データの投入・運営アカウント発行・管理API（F17）・店舗詳細やメニュー（F04）は実装しない。実店舗データや架空の本番seedは追加しない。テストでは専用PostgreSQLに明示的なテスト店舗だけを作る。
