# 仕様：配達を受ける（F-14）

対象は S-D02 の配達待ち一覧、S-D03 の詳細と受注、S-D04 の担当中注文・受け取り・配達完了、S-D05 の配達履歴。

## API

すべて現在のセッション、配達員ロール、メール確認、アカウント停止状態、配達員登録を確認する。Cookie の変更要求には信頼する Origin が必要。レスポンスは `no-store`。

| メソッド | パス                          | 結果                                                            |
| -------- | ----------------------------- | --------------------------------------------------------------- |
| GET      | `/courier/orders`             | 調理中・準備完了で担当者なしの注文。休止中は空配列              |
| GET      | `/courier/orders/current`     | 本人が担当する調理中・準備完了・配達中の注文、または null       |
| GET      | `/courier/orders/:id`         | 配達待ち、または本人が担当する注文の詳細。他の担当者の注文は404 |
| POST     | `/courier/orders/:id/accept`  | 本人を担当者として保存し、詳細を返す                            |
| POST     | `/courier/orders/:id/receive` | 担当者が準備完了の注文を受け取り、配達中にする                  |
| POST     | `/courier/orders/:id/photo`   | 担当者が配達中の置き配写真を保存する                            |
| POST     | `/courier/orders/:id/deliver` | 担当者が配達中の注文を配達完了にする                            |
| GET      | `/courier/orders/history`     | 本人が配達完了にした注文を新しい順に最大100件返す               |

一覧は注文日時・IDの昇順。店舗名と、保存済み店舗座標から注文時のお届け先座標までの直線距離（メートル）を返す。端末の現在地・道路距離は使わない。詳細は店舗住所、お届け先、注文時の商品名・価格・数量、受け取り方法を表示する。配達メモ（R-15）と連絡用電話番号は担当する本人にだけ返し、担当前はキーを含めない。決済情報・注文者 ID・メールアドレスは返さない。

## 担当の保存（R-11）

`orders.courier_id` に担当配達員のユーザー ID を保存する。F-19 の注文管理と共通のカラムを使い、配達員登録は `couriers` で再確認する。担当時の注文進捗は変更しない。

受注はトランザクション内で現在の利用者と配達員登録を再確認してロックし、配達員行と注文行のロックで同一配達員の複数受注と同じ注文の取り合いを直列化する。調理中・準備完了・配達中の担当者には部分一意インデックスも設ける。配達完了・キャンセルの担当履歴は保持し、次の受注を妨げない。

休止中は `COURIER_UNAVAILABLE`、別の担当中注文がある場合は `COURIER_BUSY`、他の担当者が決まった場合や配達待ちでなくなった場合は `ORDER_ALREADY_ASSIGNED`（いずれも409）。存在しない注文は404、UUID形式不正は400。本人の担当中注文への再送は、休止中でも同じ担当結果を返す。F-14 API は担当解除と外部決済を実行しない。

## 受け取り・配達完了・履歴（F-15）

受け取りは担当者本人の `ready` 注文だけを `delivering` にし、配達完了は同じ担当者の `delivering` 注文だけを `delivered` にする。注文行をロックして状態を検証し、更新と `order_status_history` の記録を同一トランザクションで行う。同じ操作の再送は成功として扱い、履歴を重複作成しない。担当外・存在しない注文は同じ404、許可されない状態遷移は409。

配達履歴は本人が担当した `delivered` の注文に限り、配達完了時刻・店舗名・合計金額を最大100件、新しい順で返す。置き配は写真の保存を確認してから完了できる。写真未送信は `409 DELIVERY_PHOTO_REQUIRED`。手渡しには写真を要求しない。

## アプリ

稼働中のホームに配達待ち一覧を表示し、選択すると詳細を表示する。「担当になる」の成功後は担当中の配達を表示する。競合や対象消失は一覧に戻して理由を知らせる。通信失敗は成功扱いにせず、「一覧・担当中の配達を再確認」で保存済みの結果を取得できる。

担当中の注文はホーム再表示・アプリ復帰時にも取得する。二重操作を防ぎ、画面離脱・休止・稼働切替・利用者変更で古い非同期結果を破棄する。画面を離れると AppState の購読を解除する。

## 置き配写真（F-15 / R-15）

`POST /courier/orders/:id/photo` は共有契約の JSON `{ mimeType: 'image/jpeg', base64 }` を受け取る。本文上限はこのパスだけ約2.8MB、他のAPIは従来の16KB。JPEGのみ・復号後2MiB以内・最大2000万画素を検証し、実データをデコードする。長辺1600px以内のJPEGに再エンコードしてEXIF・GPSなどのメタデータを除去する。破損・実形式違いは422、本文超過は413。不正契約は400。

送信ごとに現在の権限・登録・担当者と `delivering` / `leave_at_door` を確認する。注文行のロック内で保存し、同じ注文の再送は1枚を置き換える。配達完了後の変更は拒否する。担当解除後に別の配達員が担当した場合、前任者の写真は利用できず、現担当者の送信が必要。保存失敗は成功として返さず、トランザクションを戻す。通信結果が不明なら「一覧・担当中の配達を再確認」で `hasDeliveryPhoto` を確認し、必要なら再送する。

配達員アプリは背面カメラの許可、撮影、プレビュー、撮り直し、明示送信を提供する。確認済みの `hasDeliveryPhoto` があるときだけ置き配の完了操作が有効になる。手渡しの操作は従来通り。撮影の端末キャッシュは取得後に削除し、送信前写真は画面内メモリーだけに保持する。画面離脱・バックグラウンド・利用者変更後の撮影結果を反映・送信しない。

## 保存先・配備・保存期間

リポジトリのデプロイ想定はNode.js APIとPostgreSQLで、オブジェクトストレージの配備・資格情報は定義されていない。既存の公開メニュー画像配信は住所を含み得る置き配写真には利用しない。実装は注入可能な `DeliveryPhotoStorage` と、同一DBトランザクションを使うPostgreSQLアダプタ。`delivery_photos` に注文ごと1行、JPEGのbase64・送信配達員・有効期限を保存する。メモリーや一時ファイルを本番の保存先として使わない。

配備時は次を実施する。

1. `pnpm --filter @repo/db db:migrate` で専用テーブルと期限索引を適用する。
2. DB容量・WAL・バックアップの増加を確認して、APIに `DELIVERY_PHOTO_STORAGE=postgres` を明示設定する。base64は画像の約4/3の容量を使う。初期値 `disabled` ではアップロードと置き配完了を503で停止し、写真を保存したようには表示しない。手渡しは停止しない。
3. APIを継続稼働させ、起動時と最大60秒間隔で動く期限切れ削除の失敗ログを監視する。複数APIインスタンスからの削除は冪等。停止中に期限を迎えた写真は次回起動で削除する。無効設定でも既存写真の削除ジョブは動く。
4. API/DB通信とDBの保存領域・バックアップを保護する。バックアップに残る削除済み画像の保存期間・失効処理は配備先の運用で設定する。秘密値の追加・埋め込みは不要。
5. カメラ権限を含めて配達員アプリを再ビルドし、実端末で許可・拒否・撮影・送信を確認する。

配達完了を保存するトランザクション内で、その時点から30日後を写真の期限にする。未完了・キャンセルで残った写真も送信から30日で削除対象になる。期限到達後は削除ジョブの実行前でも参照不可、実データは次のジョブで削除する。再送した配達完了では期限を延長しない。

注文者の認証済み `GET /orders/:id` だけが、本人の `delivered` / `leave_at_door` の有効写真を `deliveryPhotoUrl` の `data:image/jpeg;base64,...` として返す。写真の公開URLやトークン付きURLは作らない。応答は `no-store` で、Web・注文者アプリは既存の写真欄に表示する。注文者のJSONと写真は同じ認可を通り、Bearerを画像コンポーネントのpropsへ公開しない。写真を含む詳細のポーリングはその分の転送量が増えるため、規模拡大時は私有オブジェクトストレージと認証付き個別取得への移行を検討する。

## 確認範囲

専用の実PostgreSQLと合成データで、写真送信・本人限定表示・完了との競合・再送・権限変更・不正画像・保存失敗のロールバック・期限切れの参照拒否と削除を確認する。決済は呼ばない。カメラSDKと端末ファイル削除は注入したコンポーネントテストで、撮影確認・権限拒否・画面離脱後の結果破棄を確認する。

iOS向けExpoバンドルの生成は確認済み。実iOS Simulatorの操作は自動化の画面取得エラー（アクセシビリティ取得不可 / `cgWindowNotFound`）により未確認で、実操作MP4の添付は保留。実端末のカメラ撮影・アップロードとデザイン照合も未確認。Expo Webや模擬画面を実操作動画の代わりにしない。
